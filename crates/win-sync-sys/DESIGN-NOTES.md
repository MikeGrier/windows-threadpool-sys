# Design notes: win-sync-sys (Tier 1)

Current canonical decisions for this crate. See [README.md](README.md) for what it is and
[CHECKLIST.md](CHECKLIST.md) for what is planned.

Repository-level decisions this crate sits under: the `win-` prefix and what `-sys` promises, both in
the workspace [DESIGN-NOTES.md](../../DESIGN-NOTES.md#new-crates-take-the-win-prefix). The crate was
proposed on 2026-10-07 when durable-ioring's readiness event
([DI-D-28](../durable-ioring/DESIGN-NOTES.md#di-d-28)) needed an event it could create and set
without `unsafe`, and the engineer chose a new crate over adding one to `windows-threadpool-sys`,
which exists to wrap the thread pool and nothing else.

## Decision index

| ID | Decision |
|---|---|
| <a id="ws-d-1"></a>WS-D-1 | **The crate's area is Win32's "Synchronization" API, and it starts with the kernel objects -- handle-based objects any thread or process can wait on.** Microsoft Learn's [Synchronization Functions](https://learn.microsoft.com/en-us/windows/win32/sync/synchronization-functions) divides the area into fourteen groups, which fall into three kinds. **Kernel objects and waiting on them** -- events, semaphores, mutexes, waitable timers, the wait functions, and `QueueUserAPC` as what ends an alertable wait -- are this crate's core. **In-process primitives** -- SRW locks and condition variables, critical sections, one-time initialization, barriers, `WaitOnAddress` -- are structures in the caller's memory rather than handles, cannot move once in use, and so pose a different design problem (pinning); the engineer chose to **omit them to start with** (2026-10-07), which parks them rather than rejecting them. **Outside the crate:** interlocked functions (Rust's atomics compile to the same instructions, so a wrapper adds nothing); timer-queue timers (the legacy API the thread pool's timers replaced, which `windows-threadpool-sys` wraps); `GetOverlappedResult` and `GetOverlappedResultEx` (overlapped I/O's, so `windows-overlapped-io-sys`'); and singly-linked lists (a lock-free stack with its own alignment rules, closer to `windows-waitable-queues`' subject). **Not decided:** named objects, `OpenEvent`, and private namespaces, which cross process boundaries -- raised with the engineer and not yet answered, so every constructor here creates an unnamed object and nothing binds to that being permanent. |
| <a id="ws-d-2"></a>WS-D-2 | **`Event` comes first, alone.** The engineer's sequencing, 2026-10-07. The other kernel objects and the wait functions follow as their own items in [CHECKLIST.md](CHECKLIST.md) -- sequenced after, not dropped. `Event` has no `wait` of its own in the first item for the same reason: waiting is the wait functions' item, and an event's wait is one case of it. |
| <a id="ws-d-3"></a>WS-D-3 | **`PulseEvent` is not offered, because it gives a wrong answer rather than a slow one.** Its own documentation says it "is unreliable and should not be used" and "exists mainly for backward compatibility" ([PulseEvent](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-pulseevent)). The mechanism it gives: a thread waiting on the event can be momentarily removed from the wait by a kernel-mode APC, and a pulse that lands in that window releases nothing, because `PulseEvent` releases only the threads waiting at the instant it is called. A waiter can therefore miss a signal it was waiting for, and nothing reports that it did. The same page notes that a wait-for-all on several objects can see the pulse come and go without returning. Microsoft's replacement is a condition variable. This is a removal on analytic grounds -- an operation that silently does the wrong thing -- not on a measurement, which is the ground the repository accepts for foreclosing an option. |
| <a id="ws-d-4"></a>WS-D-4 | **An `Event` owns a handle to an event object, and the load-bearing half of that is "an event", because a safe conversion into the thread pool's wait target depends on it.** Ownership alone -- what std's `OwnedHandle` already gives -- is what makes `set` and `reset` memory-safe: the handle is valid, and `SetEvent` on a valid handle to some other kind of object simply fails. Event-ness makes them *correct* rather than safe. It becomes a safety property one layer up: the thread pool treats a wait on a **mutex** as undefined behaviour, so `windows-threadpool-sys` can accept an `Event` without `unsafe` only because an `Event` is never a mutex ([WS-D-5](#ws-d-5)). Therefore **adopting an existing handle is `unsafe`** (`Event::from_owned_handle`): the caller vouches that it is an event, and that it carries `SYNCHRONIZE` access. The second clause is conservative: what the pool does with a handle it cannot wait on is not documented, and an `Event` must be safe to hand it. A handle lacking `EVENT_MODIFY_STATE` is permitted -- `set` and `reset` then fail with an error, which is the error path their tests traverse. No checked adoption is offered: telling whether a handle is an event means asking the kernel for the object's type, a native-API question this crate has not taken up; the option stays open. |
| <a id="ws-d-5"></a>WS-D-5 | **`windows-threadpool-sys` depends on this crate, never the reverse; the conversion into the pool's wait target lives there.** The pool waits on synchronization objects, so the arrow runs from the pool to the objects. `windows-threadpool-sys` provides `From<Event> for WaitableHandle`, and `WaitableHandle::event` is built on `Event`, so the crate creates no event of its own. A pool-owned event is signalled through a clone the caller keeps (`Event::try_clone`, a duplicate handle to the same object), which needs no `unsafe` -- unlike signalling through the borrowed handle the wait hands back, which is what its examples did before. When `Mutex` is added it gets **no** such conversion, so the pool's one undefined case stays unrepresentable in safe code. |
