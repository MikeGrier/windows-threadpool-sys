# Design notes: win-sync-sys (Tier 1)

Current canonical decisions for this crate. See [README.md](README.md) for what it is and
[CHECKLIST.md](CHECKLIST.md) for what is planned.

Repository-level decisions this crate sits under: the `win-` prefix and what `-sys` promises, both in
the workspace [DESIGN-NOTES.md](../../DESIGN-NOTES.md#new-crates-take-the-win-prefix). The crate was
proposed on 2026-10-07 when durable-ioring's readiness event
([DI-D-28](../durable-ioring/DESIGN-NOTES.md#di-d-28)) needed an event it could create and set
without `unsafe`, and the engineer chose a new crate over adding one to `windows-threadpool-sys`,
which exists to wrap the thread pool and nothing else.

## Decision index

| ID | Decision |
|---|---|
| <a id="ws-d-1"></a>WS-D-1 | **The crate's area is Win32's "Synchronization" API, and it starts with the kernel objects -- handle-based objects any thread or process can wait on.** Microsoft Learn's [Synchronization Functions](https://learn.microsoft.com/en-us/windows/win32/sync/synchronization-functions) divides the area into fourteen groups, which fall into three kinds. **Kernel objects and waiting on them** -- events, semaphores, mutexes, waitable timers, the wait functions, and `QueueUserAPC` as what ends an alertable wait -- are this crate's core. **In-process primitives** -- SRW locks and condition variables, critical sections, one-time initialization, barriers, `WaitOnAddress` -- are structures in the caller's memory rather than handles, cannot move once in use, and so pose a different design problem (pinning); the engineer chose to **omit them to start with** (2026-10-07), which parks them rather than rejecting them. **Outside the crate:** interlocked functions (Rust's atomics compile to the same instructions, so a wrapper adds nothing); timer-queue timers (the legacy API the thread pool's timers replaced, which `windows-threadpool-sys` wraps); `GetOverlappedResult` and `GetOverlappedResultEx` (overlapped I/O's, so `windows-overlapped-io-sys`'); and singly-linked lists (a lock-free stack with its own alignment rules, closer to `windows-waitable-queues`' subject). **Not decided:** named objects, `OpenEvent`, and private namespaces, which cross process boundaries -- raised with the engineer and not yet answered, so every constructor here creates an unnamed object and nothing binds to that being permanent. If they are taken up, this crate is their home: Learn lists "Private namespace functions" among the Synchronization groups, and `windows-namespace-request-sys` is about the file-system namespace, not the kernel object namespace. **Nothing needs to change in advance** (checked 2026-10-07): a named event is still an event, so `Event` holds it unchanged; creating and opening by name are new constructors beside `Event::new`, with an outcome saying whether the event was created or opened; WS-D-4 survives because Windows refuses to create or open an event under a name another kind of object holds; and boundary descriptors and private namespaces are new types with their own close routines. Two questions would come with the work: whether opening always adds the `SYNCHRONIZE` access WS-D-4 requires, and where an owned security-attributes type lives -- `windows-namespace-request-sys` has one (`SecurityDescriptor`, `SecurityAttributes`), and a named object needs one, but this crate depending on a file-request crate for it would be the wrong coupling. Moving it to a lower crate and re-exporting it from the old one would not break that crate's users. |
| <a id="ws-d-2"></a>WS-D-2 | **`Event` comes first, alone.** **Amended by [WS-D-6](#ws-d-6): the single-object wait was the first of the wait functions taken up.** The engineer's sequencing, 2026-10-07. The other kernel objects and the wait functions follow as their own items in [CHECKLIST.md](CHECKLIST.md) -- sequenced after, not dropped. `Event` has no `wait` of its own in the first item for the same reason: waiting is the wait functions' item, and an event's wait is one case of it. |
| <a id="ws-d-3"></a>WS-D-3 | **`PulseEvent` is not offered, because it gives a wrong answer rather than a slow one.** Its own documentation says it "is unreliable and should not be used" and "exists mainly for backward compatibility" ([PulseEvent](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-pulseevent)). The mechanism it gives: a thread waiting on the event can be momentarily removed from the wait by a kernel-mode APC, and a pulse that lands in that window releases nothing, because `PulseEvent` releases only the threads waiting at the instant it is called. A waiter can therefore miss a signal it was waiting for, and nothing reports that it did. The same page notes that a wait-for-all on several objects can see the pulse come and go without returning. Microsoft's replacement is a condition variable. This is a removal on analytic grounds -- an operation that silently does the wrong thing -- not on a measurement, which is the ground the repository accepts for foreclosing an option. |
| <a id="ws-d-4"></a>WS-D-4 | **An `Event` owns a handle to an event object, and the load-bearing half of that is "an event", because a safe conversion into the thread pool's wait target depends on it.** Ownership alone -- what std's `OwnedHandle` already gives -- is what makes `set` and `reset` memory-safe: the handle is valid, and `SetEvent` on a valid handle to some other kind of object simply fails. Event-ness makes them *correct* rather than safe. It becomes a safety property one layer up: the thread pool treats a wait on a **mutex** as undefined behaviour, so `windows-threadpool-sys` can accept an `Event` without `unsafe` only because an `Event` is never a mutex ([WS-D-5](#ws-d-5)). Therefore **adopting an existing handle is `unsafe`** (`Event::from_owned_handle`): the caller vouches that it is an event, and that it carries `SYNCHRONIZE` access. The second clause is conservative: what the pool does with a handle it cannot wait on is not documented, and an `Event` must be safe to hand it. A handle lacking `EVENT_MODIFY_STATE` is permitted -- `set` and `reset` then fail with an error, which is the error path their tests traverse. No checked adoption is offered: telling whether a handle is an event means asking the kernel for the object's type, a native-API question this crate has not taken up; the option stays open. |
| <a id="ws-d-5"></a>WS-D-5 | **`windows-threadpool-sys` depends on this crate, never the reverse; the conversion into the pool's wait target lives there.** The pool waits on synchronization objects, so the arrow runs from the pool to the objects. `windows-threadpool-sys` provides `From<Event> for WaitableHandle`, and `WaitableHandle::event` is built on `Event`, so the crate creates no event of its own. A pool-owned event is signalled through a clone the caller keeps (`Event::try_clone`, a duplicate handle to the same object), which needs no `unsafe` -- unlike signalling through the borrowed handle the wait hands back, which is what its examples did before. When `Mutex` is added it gets **no** such conversion, so the pool's one undefined case stays unrepresentable in safe code. |
| <a id="ws-d-6"></a>WS-D-6 | **The wait functions begin with `wait_for_single_object`, over any `AsHandle`, and `Event` still has no `wait` method of its own.** The assistant's choice, 2026-10-12, queued for the engineer's review in durable-ioring's `DI-9.7`. Raised by that crate's `DI-7.3`, whose pumped delivery has the consumer's own thread wait on a backend's notification, a handle, in a crate that forbids `unsafe`; [WS-D-2](#ws-d-2) sequenced the wait functions after `Event`, and this is the first of them taken up, the rest of `WS-1+.1` staying where the engineer parked it. **Over any handle**, because the wait is what `WaitForSingleObject` is, and the ring's completion event reaches durable-ioring as an `OwnedHandle`, not an `Event`; an `Event::wait` would be one more door onto the same call, and a `Waitable` trait over every object is the parked item's design, which one function does not pre-empt. **`WaitOutcome` has `Abandoned`**, though no event is ever abandoned: the function is over any handle, and answering `Signalled` for a mutex whose owner died would be a wrong answer, not a slow one. It is non-exhaustive so the alertable wait's third ending can join it. **A satisfied wait changes the object** -- an auto-reset event is consumed -- and the documentation says so, since a poll with `Duration::ZERO` is also a wait. **A timeout rounds up** to whole milliseconds so a nonzero wait is never a poll, and **one the call cannot express is refused**: `INFINITE` is `u32::MAX`, so a finite wait may not be that many milliseconds, and shortening it would end a wait early without saying so. **Not alertable**, so a queued APC does not end it; `WaitForSingleObjectEx` is the parked item's. |
