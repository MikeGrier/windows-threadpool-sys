# Design notes: durable-ioring (Tier 1)

Current decisions for this component. See [COMPONENT.md](COMPONENT.md) for what it is and
[CHECKLIST.md](CHECKLIST.md) for what is planned. This component keeps Tier 1 only for now, with the
rationale folded into each decision, as [windows-ioring-sys](../windows-ioring-sys/DESIGN-INSTRUCTIONS.md)
does. The conversation that produced these decisions is the Tier 3 record,
[DESIGN-SESSION-2026-10-05-epoch-ring.md](../../design-sessions/DESIGN-SESSION-2026-10-05-epoch-ring.md),
which also holds the working positions and questions that are **not** decided and therefore do not
appear here.

## Decision index

| ID | Decision |
|---|---|
| <a id="di-d-1"></a>DI-D-1 | **A separate crate, layered directly on `windows-ioring-sys`'s `IoRing` -- not on the domain runtime.** This is the durability crate C-3 of the [2026-08-30 session](../../design-sessions/DESIGN-SESSION-2026-08-30-numa-sharded-io-execution-domains.md) planned, and it honours [D-54](../windows-ioring-sys/DESIGN-NOTES.md#d-54) and [D-26](../windows-ioring-sys/DESIGN-NOTES.md#d-26): durability groups and durability policy live here, never in the ring crate. **What changed is the substrate.** `M33+.5` described a layer that "contains a domain and submits through it"; the domain runtime is parked behind M32 and the topology planner, and none of the questions gating it bear on durability, so building on the ring directly removes a dependency the work does not have. C-3's per-domain constraint survives by construction: one dioring instance carries one durability sequence, and a consumer spanning two instances gets no single durability point across them. Whether a future domain contains a dioring, or the reverse, is not decided. `M33+.5` is transferred here accordingly. |
| <a id="di-d-2"></a>DI-D-2 | **The package is named `durable-ioring` (crate identifier `durable_ioring`; "dioring" for short).** Named for the feature rather than the mechanism, in the engineer's words: "the top line feature is the durability; the epoch is just how we are achieving it". `epoch-ring` was considered and rejected on that ground. The objection that "durable" names an outcome the crate cannot guarantee -- durability rests on the device honouring the flush -- is answered by the contract, which must say plainly what is assumed rather than guaranteed, not by the name. No `-sys` suffix: in this workspace that suffix marks thin, unsafe-bearing wrappers over Win32 ([DI-D-4](#di-d-4)). **No `win-` prefix, because this is a new facility rather than a Windows API made safe.** The workspace rule [New crates that layer directly over Windows APIs take the `win-` prefix](../../DESIGN-NOTES.md#new-crates-take-the-win-prefix) covers crates that layer safe abstractions more or less directly over Windows APIs; this crate is a durability layer built on such crates, which, in the engineer's words, "does not fit the mold". The rule's wording originally read as covering every new crate; this case prompted the engineer to clarify its scope on 2026-10-05, and the amended text names this crate as the example. |
| <a id="di-d-3"></a>DI-D-3 | **Strictly Windows-only, under the workspace's existing rule.** Every item `cfg(windows)`, no portability layer, no cross-platform code. The engineer's consumers also run on Linux behind their own abstraction, and the session records how the design compares with io_uring as context for that work; none of it is a requirement here. One consequence is retained because it costs nothing and adds no platform: **the contract is written in terms of durability, not in terms of Windows' incidental behaviour.** [D-47](../windows-ioring-sys/DESIGN-NOTES.md#d-47-detail)'s one-sided barrier is a floor this crate's implementation must cope with, not a property it promises its consumers. |
| <a id="di-d-4"></a>DI-D-4 | **Amended by [DI-D-29](#di-d-29): the owning form a consumer gives is `SharedHandle`, which dioring hands to the ring unchanged.** **No unsafe code, enforced by `#![forbid(unsafe_code)]` from the first commit.** The `epoch_log` sample needs `unsafe` only because it pushes through raw handles; this crate takes files in owning forms (`SharedHandle`, `RegisteredFile`, `flush_owned`) and never a `RawHandle`, which its per-write bookkeeping wants anyway for file identity. If a Win32 call is ever needed that no lower crate wraps safely, the safe wrapper is added to the lower crate (the workspace's fix-the-layer policy), never an `unsafe` block here. A build that fails on the `forbid` is the moment to raise it, not a lint to relax. |
| <a id="di-d-5"></a>DI-D-5 | **Two consumer classes, and a layering that serves both: this crate reports and resolves; retention is a layer above it.** Naive consumers want durability without expertise; expert consumers -- storage engines with their own logs -- want truthful reporting and no buffering imposed on them. So this crate owns, for both:<br><br>**(a)** a high-water mark that never reports a point durable while an earlier failure is unresolved -- Scenarios 1 and 2 in the session show a later successful flush reporting data durable that is gone, and an expert needs this guarantee as much as anyone;<br><br>**(b)** a resolution protocol by which the consumer, not this crate, decides what a failure means;<br><br>**(c)** an inventory, by identity, of the writes a failure puts in doubt -- a fact about what was issued, not a policy about what to do.<br><br>Retaining written data until durable, rewriting it, and replaying it are **policy, and belong to a separate future crate above this one**, which uses (b) and (c) rather than re-tracking every write. A naive consumer on this crate alone gets truthful durability and a precise loss report -- correct, if not graceful; the retention crate is what makes it graceful. That crate is a deliberate layer, not work deferred for want of a consumer, and is queued in [CHECKLIST.md](CHECKLIST.md). |
| <a id="di-d-6"></a>DI-D-6 | **Ordering overlapping writes is the consumer's responsibility; this crate tracks an identity per write and nothing more.** The engineer's decision. Two overlapping writes in flight together land in an unspecified order, and replaying suspect writes after a failure can clobber newer data if overlaps are not resolved newest-wins; both are the consumer's to handle, and the contract states the first as a requirement on the consumer. This crate does not track in-flight byte ranges, refuse overlaps, or resolve them. Whether the per-write identity carries an order usable for newest-wins resolution was left open here; it does -- `OpId` is ordered by push order ([DI-D-15](#di-d-15)). **Applied 2026-10-06 (the engineer: "drop the extents. The consumer may track them themselves via the OpId."):** a failure's `SuspectWrite` and the durability provider's request (DI-2.12) carry a write's `OpId`, never its offset or length. |
| <a id="di-d-7"></a>DI-D-7 | **The `epoch_log` sample stays as it is until this crate is proven; then a merge-or-delete decision is taken.** The repository's duplicate-then-decide rule: this crate is a new path beside the sample, not a rewrite of it. The decision -- rebuild the sample on this crate, keep both, or retire one -- is queued in [CHECKLIST.md](CHECKLIST.md) so the duplication cannot become permanent by default. A defect the session found in the sample's own reasoning is queued separately in the ring crate, since it is wrong whatever happens here. |
| <a id="di-d-8"></a>DI-D-8 | **Amended by [DI-D-9](#di-d-9): a durability point is now identified by the consumer's own ordered number, and what stays opaque is the mechanism, not the identity.** As first written: durability points are opaque to the consumer -- the consumer names and waits on a point without seeing how it is represented, so the epoch stays an implementation detail ([DI-D-2](#di-d-2)). That intent survives DI-D-9: which flushes are issued, under which commit strategy, and how the suspect window is tracked remain dioring's and invisible; only the *label* of a point became the consumer's. |
| <a id="di-d-9"></a>DI-D-9 | **Amended by [DI-D-27](#di-d-27): rule (c)'s "covered" now means named in a durability-provider call.** **Amended by [DI-D-19](#di-d-19): every rule below applies within one lineage. A write's epoch is a lineage plus an epoch id (formerly "epoch number"), and a seal covers only its own lineage's prefix.** **The durability model: the consumer tags each write with an epoch id of its own choosing, and `make_durable_through(n)` seals and requests durability for every epoch at or below `n`.** The engineer's decision, reached as a what-if and then adopted. Tags may be issued in any order, higher and lower intermixed; a journal transaction ID or log sequence number can be the tag directly. `make_durable_through(n)` seals a *prefix* of the number space, so "n durable implies every m < n durable" holds by construction and epochs above `n` remain open -- several open epochs come free, with no open or seal ceremony and no handles. Rules:<br><br>**(a)** once `n` is sealed, a write tagged at or below `n` is an API violation, refused before anything is reserved, as [D-28](../windows-ioring-sys/DESIGN-NOTES.md#d-28) treats every legality check;<br><br>**(b)** `make_durable_through(m)` with `m` at or below an already-sealed number is a no-op that reports `m`'s current state -- durable, pending, or failed -- rather than a single "already durable" code that would be false in two of the three cases;<br><br>**(c)** writes of still-open epochs that a commit's flush happens to cover are not reported durable, and may appear in a failure's suspect set with their tags -- they are simply not yet guaranteed.<br><br>Why it fits: a covering flush covers everything pushed before it whatever its tag, so the prefix is the physical truth of the ring and the tag is bookkeeping over it; and because rule (a) forces a rewrite of a failed epoch's data to carry a higher tag, healing composes with it without a special rule. Named in a storage idiom rather than a database one (prepare/commit): **"through" states the prefix property in the name**, and the report is `durable_through()` (the high-water mark the sample already calls by that name). Costs carried: a bare number compares across instances, losing a type-level guard on C-3's per-domain rule (since answered in the DI-2.1 draft by making the epoch type generic, so the consumer chooses comparability through types); sparse tags mean an ordered map of open epochs inside dioring; a consumer whose native sequence wraps (jbd2's 32-bit transaction IDs do) maps it onto a non-wrapping one. The tag's concrete type is [DI-2.1](CHECKLIST.md)'s. **Supersedes the explicit-handle model** explored in the session (open and seal as separate operations, positions assigned at seal), which this model makes unnecessary. |
| <a id="di-d-10"></a>DI-D-10 | **The consumer cannot put an operation on the ring that interferes with dioring's control of it.** The engineer's decision. dioring owns its ring outright: the consumer reaches it only through dioring's own operations -- reads, tagged writes, and durability requests -- and never through `IoRing`, `Batch`, a `RingScope`, or `windows-ioring-sys`' raw-SQE seam ([D-7](../windows-ioring-sys/DESIGN-NOTES.md#d-7)). Anything that would interfere -- a flush whose failure the suspect window would not hear, a cancel that silently changes a tagged write's fate, a registration that replaces what dioring registered -- either is not offered or is offered only as a dioring-mediated operation whose effect dioring accounts for. **Enforced by the types, not by documentation**: no public method returns a borrow through which an underlying ring operation can be pushed, which is the same shape as [D-43](../windows-ioring-sys/DESIGN-NOTES.md#d-43)'s `RingScope` and is checked by the borrow question in [DESIGN-INSTRUCTIONS.md](../windows-ioring-sys/DESIGN-INSTRUCTIONS.md). **No escape hatch, including for experts**, and this is consistent with OPTION INTEGRITY rather than an exception to it: that rule permits foreclosing an option on a demonstrated wrong answer, and an interfering operation produces exactly that -- a durability report that is false. |
| <a id="di-d-11"></a>DI-D-11 | **Rebinding a file to a new handle is not this layer's; a handle that goes bad is ordinary failure.** The engineer's decision: rebinding is a nice capability but heavyweight, and does not belong here. So dioring has no "handle is dead" state and no recovery path of its own for it: operations on a bad handle complete with errors, a failed write takes the failure path every write takes, and the consumer resolves -- typically by abandoning in this instance and rewriting the suspect ranges through a new instance over a reopened file, which the `Failed` event's inventory makes possible. **One obligation follows, and it replaces the earlier non-foreclosure constraint:** the inventory must name files in terms the consumer can use without the dead handle -- a consumer-supplied file identity, not a dioring handle -- so the report stays actionable after the handle is gone. The causes are not limited to removable media: a forced volume dismount, a locked BitLocker data volume, a detached virtual disk, a network share whose reconnect fails, and loss of an iSCSI or SAN path can all leave handles invalid. Since all of them reach dioring as errors, none needs separate handling. |
| <a id="di-d-12"></a>DI-D-12 | **Amended by [DI-D-19](#di-d-19): (f)'s high-water mark and (g)'s gates are per lineage, and a failure belongs to every lineage with a write in its suspect set, with one resolution applying in all of them. (b)'s instance-wide scope stays the default, and narrows only through caller-declared flush domains ([DI-D-21](#di-d-21)).** **Durability failures, and their resolution by the consumer.** Settled through DI-1.2's ten questions ([archived](COMPLETED-CHECKLIST.md#di-12)) and DI-2.7 point 7.<br><br>**(a) What a failure is.** A failed flush, or an external failure the consumer imports. A failed or short *write* is an ordinary operation error on its own completion, and "durable" covers only writes that completed successfully, up to the byte count each completion reported.<br><br>**(b) What it puts at risk.** Its suspect set is every write pushed before the failure was observed -- in the instance's own observation order -- that no successful flush covers; frozen at observation. Failures and epochs are many-to-many: one failure spans several epochs, and one epoch can sit in several failures.<br><br>**(c) Who decides.** The consumer resolves each failure: **heal** (its assertion that it re-issued what it needs, under higher tags; takes effect when the commit of the first seal made after the heal completes successfully), **abandon** (immediate), or **close** (the failure returns, unresolved, to the inventory). dioring never judges whether a repair was sufficient. Several failures may be resolved in one call, atomically and validated whole; a refused call hands its tokens back. Resolution is per failure, not per epoch or per I/O; a prefix form remains a non-foreclosed extension, and per-I/O resolution belongs to the retention layer.<br><br>**(d) How a failure is named.** An affine, move-only **token**, dispensed with the `Failed` event or from the inventory, at most one live per failure, consumed by heal, abandon or close; dropping it is `close()`, and it is `#[must_use]`. A `Copy` **identity**, never reused within an instance, names a failure in events and queries. Another instance's token or identity is refused.<br><br>**(e) What can be asked.** Unresolved failures are enumerable and queryable for identity, cause and suspect set. A resolved failure leaves no memory; since identities are never reused, an identity no longer present means resolved.<br><br>**(f) What the high-water mark means.** It may pass an abandoned epoch: `durable_through(m)` means every epoch at or below m is durable *or was abandoned*. An epoch passes only when every failure containing it is resolved; it is durable only if every one was healed, and abandoned if any was abandoned. A never-resolved failure stalls the high-water mark, and no timeout is invented ([D-67](../windows-ioring-sys/DESIGN-NOTES.md#d-67)).<br><br>**(g) Gated operations.** An operation held for release-after-durable on epoch n is released when the high-water mark reaches n and n is durable; if n is abandoned it fails, its error saying it was *never issued*. Gates wait for durable, never for merely resolved. (Derived from DI-1.2 Q1 and Q5, and confirmed by the engineer.)<br><br>**(h) Imports.** In v1, on the engineer's condition that the state graph stays reducible: an import is the same "failure observed" transition as a failed flush, with the cause as data and no state or edge of its own. It cannot retract a `Durable` already reported. |
| <a id="di-d-13"></a>DI-D-13 | **Amended by [DI-D-30](#di-d-30): a fifth synthesized event, `LineageEnded`.** **Amended by [DI-D-27](#di-d-27): a request is answered once its writes have completed and the durability providers it needs have answered; one waiting on a provider that has not answered stays pending, reported through ETW ([DI-D-26](#di-d-26)), not silently.** **dioring presents its own completion queue, carrying the consumer's completions and the durability events it synthesizes.** Approved by the engineer under DI-1.2 Q2. The kernel ring's queue is dioring's alone ([DI-D-10](#di-d-10)); the consumer pops dioring's, which holds every completion a consumer should observe plus four synthesized events: `Failed`, `Blocked`, `Durable` and `Abandoned`. **Ordering:** `Durable { through: n }` is delivered after the completions of every write tagged at or below n. **Every `make_durable_through` gets a prompt answer** -- `Durable`, `Failed` or `Blocked` -- never a silent stall; `Blocked` is emitted when a request's flushes succeeded but an unresolved failure sits at or below it, names that failure, and is followed by `Durable` once the failure is resolved. Synthesizing `Blocked` must be cheap, so a consumer that does not care can ignore it. No filtering is offered: the only synthesized event beyond the four outcomes arises only in failure cases, to be revisited if a noisy class of synthesized entries ever appears. Concrete types are DI-2.1's. |
| <a id="di-d-14"></a>DI-D-14 | **Amended by [DI-D-19](#di-d-19): the scope becomes one *lineage*. Independent durability counters use separate lineages within one instance; a client that wants no interaction at all still uses a separate instance.** **An epoch id's scope is one instance, and each instance's epoch space has one author.** Approved by the engineer (DI-2.8), with the instruction that this scope be well documented -- it is stated in [CONTRACT.md](CONTRACT.md) under Terms and under what the contract requires of the consumer. The same number on two instances names two unrelated epochs; dioring never relates them, and any meaning a consumer gives a number across instances -- one LSN space for a log ring and a data ring, as [API.md](API.md) shows -- and any join between them is the consumer's. Because `make_durable_through(n)` seals every number at or below n, independent clients cannot share an instance's epoch space unless they share one allocator: partitioning the numbers fails, since a prefix seal cuts across any partition. Separate instances are the expected arrangement, and they also keep commit cost and failure scope independent. Several independent sequences within one instance ("lanes") would be a feature of its own -- not proposed, not foreclosed. |
| <a id="di-d-15"></a>DI-D-15 | **Renamed by DI-2.15: `DurableRing` is now the trait ([DI-D-24](#di-d-24)); dioring's concrete type is `Dioring<B, E = u64, ...>` ([API.md](API.md) section 17). Amended by [DI-D-30](#di-d-30): the durability events are five, with `LineageEnded`.** **Amended by [DI-D-17](#di-d-17): the type gains a context and a registered-buffer parameter, and a completion's buffer becomes optional. Amended by [DI-D-20](#di-d-20): the gate moves into options taken by `_with` forms.** **The API shape for tags and the completion queue is [API.md](API.md).** Approved by the engineer (DI-2.1, 2026-10-05); API.md is the authoritative text and is not restated here. Its load-bearing choices, for finding them: the ring is **generic over its epoch type**, `DurableRing<B, E = u64>` with `E: Copy + Ord + Debug` -- the engineer's direction -- so comparability across instances is the consumer's choice through types, and the consumer owes dioring an `Ord` that is a total order and never wraps (stated in [CONTRACT.md](CONTRACT.md)); the per-instance guard sits on what dioring mints (`OpId`, `FailureId`, tokens); `OpId` is ordered by push order, which gives the retention layer its newest-wins order; writes carry their epoch as a required argument and reads and writes an optional gate, with refusals made before anything is reserved; `make_durable_through` answers an already-sealed epoch synchronously; and one `Entry` type carries operation completions and the four durability events. Names (`Entry`, `DurableRing`, `EpochTag`, `FileKey`) remain placeholders. |
| <a id="di-d-16"></a>DI-D-16 | **Until the set of changes dioring depends on is about to release, dioring consumes `windows-ioring-sys` by relative path only: `windows-ioring-sys = { path = "../windows-ioring-sys" }`, with no `version`.** The engineer's direction, 2026-10-05. dioring is built against the ring crate's unreleased tree, beginning with `M30`: [D-80](../windows-ioring-sys/DESIGN-NOTES.md#d-80) (a refused push hands back its payload, a breaking change) and [D-81](../windows-ioring-sys/DESIGN-NOTES.md#d-81) (safe file registration). No published version contains them. A `version` written now would have to guess the number release-please will choose. **This differs from the workspace's usual form** (`version` plus `path`) deliberately. A path-only dependency also makes `cargo publish` of dioring refuse until the version is pinned, so the switch cannot be skipped at publish time. **When the set is about to release:** pin the version of the `windows-ioring-sys` release that carries everything dioring relies on, keeping the `path`. That must land before dioring's own first release PR merges, or its publish job fails. Scheduled as `DI-3.1` (adopt) and `DI-3.5` (pin). |
| <a id="di-d-17"></a>DI-D-17 | **Renamed by DI-2.15: the type below is now `Dioring`, `DurableRing` being the trait ([DI-D-24](#di-d-24)); and "covered" is [DI-D-27](#di-d-27)'s.** **dioring's composition with `windows-ioring-sys` is [API.md](API.md) sections 7-10.** Approved by the engineer (DI-2.2, 2026-10-05); API.md is authoritative and is not restated here. Its load-bearing choices, for finding them: the type is `DurableRing<B, E = u64, C = (), R = Vec<u8>>`, with `C` the consumer's per-operation context, carried inside dioring's own ring sidecar; **files** given at construction are registered and held by the ring for its life, and files added later with `add_file` are not; **dioring holds the registered buffers** (the engineer: "it's fine for dioring to hold the buffers"), because a gated operation is issued later, from inside `pop` or a seal, where no consumer borrow exists -- the consumer reaches the bytes through guarded accessors, and the buffers arrive already placed, since placement is the topology planner's; the registered type `R` is separate from `B`, so that owned writes keep write-only buffer types; **`remove_file` is refused** while the file has an operation in flight or held, or a write no successful flush has covered, and the refusal is **descriptive** at the engineer's request -- `FileBusy` reports every hold and what clears it; and every refusal, including the ring's own and a failed construction, hands back what it took. A completion's buffer is `Option<B>`, `None` for a registered-span operation. Built on `windows-ioring-sys`' [D-80](../windows-ioring-sys/DESIGN-NOTES.md#d-80) and [D-81](../windows-ioring-sys/DESIGN-NOTES.md#d-81). |
| <a id="di-d-18"></a>DI-D-18 | **Amended by [DI-D-28](#di-d-28) and [DI-D-24](#di-d-24): every entry, including those no completion announced, sets dioring's own readiness event, not the ring's completion event; the front ends wait on that event (`readiness()`) and are written once over the trait.** **Completion routing: an I/O-free core with a front end per delivery model, and entries handed to the consumer strictly one at a time, in order.** Approved by the engineer (DI-2.3, 2026-10-05). The models are `windows-ioring-sys`' [D-3](../windows-ioring-sys/DESIGN-NOTES.md#d-3): **Model A, threadless dispatch**, and **Model B, dedicated domain thread**. **Shape:** the core holds epochs, failures, held operations and the entry queue, and does no I/O. `DurableRing` is the Model B front end (`&mut self`; the consumer pops, waits with a bounded `pop_within`, or waits on `completion_event` alongside other handles). The Model A front end owns the delivery, has `&self` methods usable from any thread, and hands entries to a consumer callback on a pool thread. **Ordering:** the ring crate's delivery callbacks can overlap, so the pool's order is not completion order. dioring therefore records each completion and appends its entries to its own queue under its own lock, so queue order is state order. `Durable { through: n }` is appended only once every write at or below n is *recorded* complete. A single deliverer drains the queue, so consumer callbacks never run concurrently and never run with a lock held -- this is what keeps [DI-D-13](#di-d-13)'s promise that `Durable` follows the completions it covers. **Entries no completion announced** (from `abandon`, or a refused gate) signal the ring's own completion event, so they arrive the same way as every other entry under both models. **Locks are never shared across layers** (the engineer: "do not try to share locks. bad coupling"). One lock would be better in itself, but sharing the ring's would exploit an implementation artifact, and supporting it properly would make the ring crate a synchronization provider, outside its scope. dioring takes its own lock, then the ring's. **dioring binds only to the ring's specified contract.** The lock order is safe because `EventDelivery` calls back with the ring lock released, and the ordering design assumes callbacks may overlap. Both are stated on `EventDelivery::new` and recorded as the ring crate's [D-83](../windows-ioring-sys/DESIGN-NOTES.md#d-83), its `M31.1`, which `DI-3.2.2.1`, the delivery both front ends share, took as a prerequisite. Teardown under Model A is `DI-2.7`'s. |
| <a id="di-d-19"></a>DI-D-19 | **Amended by [DI-D-22](#di-d-22): seals use completion-gated flushes only, so a ring-wide flush barrier is no longer among what lineages share.** **Durability lineages: several independent durability sequences coexist in one instance and on one ring, and they are the normal way to get independent durability.** The engineer's direction, 2026-10-05 ("i think we need this"). It answers the consequence found under DI-2.4: with one high-water mark per instance, independent durability per device needed one instance, and so one ring, per device -- "an extremely undesirable consequence of this design". A **lineage** carries what the contract so far gave an instance -- an epoch space, a seal point, a high-water mark and a failure set -- and every rule defined so far applies unchanged within a lineage. **Normal mode, not an advanced feature:** the guidance to consumers is a lineage for each independent durability counter -- per device, or per party sharing the ring. **Lineages separate durability, not everything.** The lineages of an instance still share its submission-queue capacity, its completion queue and single deliverer, dioring's lock, the failure scope of any file they both write, its lifecycle, and under Model B its thread. **A client that wants no interaction at all uses another instance** -- the engineer: "when a client wants no interaction, another instance is a safe bet." Both are first-class, and the choice is the consumer's. **Reads take no part**, except through a gate, which names a lineage's epoch. This amends [DI-D-14](#di-d-14) and reopens wherever an approved decision says "instance" for what is now a lineage's -- [DI-D-9](#di-d-9), [DI-D-12](#di-d-12), [API.md](API.md) and [CONTRACT.md](CONTRACT.md). **The specifics, settled under DI-2.9 (2026-10-05), are [API.md](API.md) section 12:** an epoch is a lineage plus an epoch id (`Epoch<E> { lineage, id }`, only `PartialOrd`), and every place the API takes or reports an epoch carries one, so the lineage comes from each write and files carry none; lineages are dioring-minted handles, minted at any time with an optional UTF-8 description, enumerable, and retirable when empty; the default lineage is real, enumerable and not retirable; gates may cross lineages; a failure belongs to every lineage with a write in its suspect set, imports name one lineage or all, and one resolution applies in all of them; `Durable` follows its own lineage's completions, with one deliverer for all lineages and nothing more promised between them. The suspect set's scope stays the instance unless the consumer declares flush regimes ([DI-D-21](#di-d-21)). |
| <a id="di-d-20"></a>DI-D-20 | **Advanced per-operation parameters ride in options values: each operation has a plain form and a `_with` form taking `WriteOptions` or `ReadOptions`.** The engineer's direction, 2026-10-05 ("do it"), after asking for Rust's convention for an optional reference to a set of advanced parameters. Rust has no optional parameters, so the plain form covers the common case and is the `_with` form with default options. The options are small `Copy` values passed by value and built with setters, following `windows-ioring-sys`' `PushOptions`, not borrowed through an `Option<&_>`, which would make the common path write `None`. Their fields are private, so adding an option is not a breaking change -- a `#[non_exhaustive]` struct with public fields would forbid struct-update syntax outside the crate. The gate moves into them from its positional place ([API.md](API.md) section 11). (A lineage override was planned for `WriteOptions`; DI-2.9 point 4 made it unnecessary, because every epoch now names its lineage.) |

A self dev-dependency enables it for every test build, so CONTRACT.md's worked examples, compiled as doctests, always run. **Not decided:** whether a write to an open epoch already abandoned should be refused; it is accepted, and the question is queued under `DI-3.2.5`, beside `GateAbandoned`. **CONTRACT.md corrected:** the many-to-many example's second ending said the mark moves past the abandoned epochs; by the contract's own resolution rule it does so once F1's heal takes effect, at the next seal, and the example now makes that seal. |
| <a id="di-d-35"></a>DI-D-35 | **A write tagged with an abandoned epoch is refused, open or sealed.** The engineer's decision, 2026-10-07 ("a write to an epoch that has been abandoned should fail"), answering the question [DI-D-34](#di-d-34) left open. Abandoning declares an epoch's writes lost, and the epoch abandoned from then on ([DI-D-12](#di-d-12) (f)); a write accepted into it afterwards would carry an epoch that can never be reported durable. The refusal is `PushRefusal::EpochAbandoned { epoch }`, made before anything is reserved and handing back the buffer and context like every refusal. An epoch at or below the seal point is refused as `Sealed`, which is checked first and remains true; `EpochAbandoned` is therefore the answer for an abandoned epoch above it, which is the case abandoning creates when a failure suspects open writes. It parallels a gate on an abandoned epoch (`GateAbandoned`, [DI-D-23](#di-d-23)): neither can ever be satisfied. The oracle checks it once the `Abandoned` entry has been observed; a write accepted between `resolve` and that entry is not judged, because the oracle cannot see the call. |

## <a id="di-d-29-a-file-is-a-sharedhandle"></a>DI-D-29: a file is a `SharedHandle`

**The type.** `SharedHandle`, from the workspace crate
[win-shared-os-owned-handle](../win-shared-os-owned-handle/README.md): std's `OwnedHandle` behind a
reference count. It is published on crates.io, so dioring depends on it by version and path.

**How it was reached.**

- 2026-10-06, DI-2.17. The engineer asked whether a canonical file type existed. None fitted:
  `std::fs::File` is not cheap to share; `windows-ioring-sys`' `SharedFile` exposed no handle, so a
  durability provider handed one could not flush out of band ([DI-D-27](#di-d-27)); and
  `windows-namespace-request-sys`' `CapturedHandle` owns a duplicate rather than sharing one. The
  first answer was a crate-local `DurableFile`.
- 2026-10-07. The engineer moved the type into its own crate, so that every crate wrapping
  `Arc<OwnedHandle>` uses one type instead of each defining its own. The crate is named
  `win-shared-os-owned-handle` and the type `SharedHandle`, both the engineer's.

**What the type gives** (its own [DESIGN-NOTES.md](../win-shared-os-owned-handle/DESIGN-NOTES.md)
is authoritative):

1. Many holders: cloning is a reference-count increment, and the handle closes when the last holder
   drops. An operation in flight, the ring's registration and a durability provider can each hold a
   file past `remove_file`, and ending the instance waits for them ([DI-D-25](#di-d-25)).
2. Lending, through `AsHandle` and `AsRawHandle`, so a consumer or a provider can call Windows on the
   file without taking ownership.
3. Conversions in from `OwnedHandle` and `std::fs::File`, and back to `OwnedHandle` for the last
   holder.
4. A same-handle test, so the same handle given under two keys is detectable.

**What the contract adds on top of the type.**

- **No I/O through it.** All I/O goes through the instance, which keeps
  [DI-D-10](#di-d-10)'s single control of the ring.
- **No open-mode inspection.** The contract does not check how a handle was opened; facts such as
  no-buffering are declared by the consumer, not queried.
- **Identity is the consumer's `FileKey`**, never the handle ([DI-D-11](#di-d-11)).
- **No duplicate on the way to the ring.** dioring hands the ring crate the same handle: the ring
  crate takes `SharedHandle` itself, its own `SharedFile` removed
  ([its D-82](../windows-ioring-sys/DESIGN-NOTES.md#d-82)).

**Considered and left out:** querying a file's volume and file id to detect the same file opened
twice. A consumer can do it through the lent handle.
