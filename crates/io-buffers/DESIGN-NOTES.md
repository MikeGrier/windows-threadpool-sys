# Design notes: io-buffers (Tier 1)

Current canonical decisions for this crate. See [README.md](README.md) for what it is and
[CHECKLIST.md](CHECKLIST.md) for what is planned.

Repository-level decision this crate sits under: the [naming
decision](../../DESIGN-NOTES.md#new-crates-take-the-win-prefix), which gives `win-` only to a crate
that raises a Windows API into safe Rust. The crate was proposed on 2026-10-12 while planning
`DI-8.2`, the split of `durable-ioring` into a portable crate and a Windows one
([DI-D-50](../durable-ioring/DESIGN-NOTES.md#di-d-50)); the engineer approved the plan.

## Decision index

| ID | Decision |
|---|---|
| <a id="ib-d-1"></a>IB-D-1 | **The crate exists so the portable core of `durable-ioring` can name the buffer contract without a Windows dependency, and it is named for the facility, `io-buffers`, with no `win-` prefix.** The engineer approved a buffer crate, 2026-10-12 ("I agree with a buffer crate"), and the plan below ("I think this is a good plan please write it up and construct the crate outline"). **Why a crate at all.** `durable-ioring`'s contract trait is bounded by `IoBuf` and `IoBufMut`, which `windows-ioring-sys` defines and gates `cfg(windows)` as a whole crate, although its buffer module, which `IB-1.1` copied and `IB-1.3` deleted, names nothing Windows. The portable crate [DI-D-50](../durable-ioring/DESIGN-NOTES.md#di-d-50) calls for cannot depend on it. **Why it is also the merge of a duplicated pair.** `windows-ioring-sys` and `windows-overlapped-io-sys` each define their own `IoBuf` and `IoBufMut`, with the same signatures, duplicated on purpose under duplicate-then-decide with the merge left open; the ring crate's `numa_buffer_io` module, deleted by `IB-1.3`, recorded why a third copy was refused. A neutral crate that owns one definition is where that merge lands, so `durable-ioring` takes the single definition and does not add a third copy. **Why not the ring crate made portable:** a portable crate would then depend on a `windows-` crate whose `lib.rs` is empty off Windows, and the contract is not about Windows. **Why not a copy in `durable-ioring`:** the unsafe promise would be stated in two places, and each ring buffer type would need an adapter to reach the ring crate's own trait. **The name** is the assistant's choice, queued for the engineer's review in durable-ioring's `DI-9.7`: the facility is I/O buffers, so it takes no `win-` prefix; `io-buffers` was not a published name when this was written (checked 2026-10-12), and `iobuf` was. |
| <a id="ib-d-2"></a>IB-D-2 | **The contract is moved from the ring crate, not rewritten.** The two traits, their unsafe obligations and the standard-type implementations keep their text and their tests when `IB-1.1` moves them, so the promise is stated once and is the one both ring crates already ship. **What changed is only the words naming the holder:** the ring crate's text said "this crate holds the value", which means nothing in a crate no ring owns, so it says "the I/O layer it was handed to". The obligations themselves are word for word. This note does not restate the obligations: they are the traits' documentation, which is the authoritative statement. `RegisteredSpan` -- a buffer index, an offset and a length, three `u32`s -- moves with them: it is data, it names a notion `io_uring` has too, and `durable-ioring`'s portable contract carries it. That inclusion is the assistant's choice, queued in `DI-9.7`. |
| <a id="ib-d-3"></a>IB-D-3 | **One concrete buffer is built here: an owned, aligned allocation, `IB-1.4`.** The engineer approved it with the plan. A target declares the alignment its buffer addresses need (`Geometry` in `durable-ioring`), unbuffered file I/O is the case that needs sector alignment, and no `IoBuf` in the workspace can promise an alignment: `Vec<u8>` has an alignment of one. The workspace has already grown copies of the thing -- `windows-namespace-request-sys`' `AlignedBuffer` ([buffer.rs](../windows-namespace-request-sys/src/buffer.rs)), which is not an `IoBuf`; an aligned allocation in [windows-overlapped-io-sys' fs.rs](../windows-overlapped-io-sys/src/fs.rs); and local `Aligned` structs in the ring crate's tests. The buffer needs only `std::alloc`, so it is portable and the unsafe allocation code lives in one place. The interface is [IB-D-6](#ib-d-6); what was fixed first is that the alignment is chosen at construction by the caller and that constructing one needs no `unsafe`. Merging the other copies into it is [IB-2+.2](CHECKLIST.md), a decision made when this one is proven. |
| <a id="ib-d-4"></a>IB-D-4 | **A platform's memory stays in the platform's crate, which implements the traits.** The engineer approved this boundary with the plan. A buffer placed on a NUMA node, backed by huge pages or registered with a kernel is a Windows or Linux facility. **Consequence for `NumaBuffer`:** `win-numa-sys` defines no buffer trait on purpose, and the ring crate implements `IoBuf` for `NumaBuffer` because it owns the trait. Once the trait lives here, neither crate owns both the trait and the type, so that implementation moves to `win-numa-sys`, which gains a dependency on this crate; `IB-1.2` does it. That ends the allocator crate's trait-free stance in one respect -- it implements a trait it does not define -- and the assistant queues it for the engineer's review in `DI-9.7`, since the stance was deliberate. **Working position, not a decision:** a portable notion of placement -- a buffer that wants node N, with Windows and Linux behind it -- may sit above this crate one day. Nothing here forecloses it, because the contract says nothing about where memory came from. It is not scheduled: a second platform's allocator does not exist yet to shape it. |
| <a id="ib-d-5"></a>IB-D-5 | **`windows-overlapped-io-sys` adopted the shared pair, on the engineer's decision (2026-10-12, "implement ib-2+.1").** It had kept its own, under duplicate-then-decide, because adopting the shared traits there changes what a type that implements both crates' traits means: it then has two implementations of one trait, which does not compile. The decision was the engineer's, made with the shared crate proven, and was tracked as `IB-2+.1` so the duplication did not become permanent by being forgotten. **What it cost:** a type implementing both crates' traits must drop one implementation -- a break for such a downstream crate, so the change is marked breaking; nothing in this workspace did, which compiling every dependent showed. **What it bought:** a buffer type is written once and used with either crate, which a test in the ring crate checks by compiling a type that implements only `io-buffers`' traits against both crates' bounds. |
| <a id="ib-d-6"></a>IB-D-6 | **`AlignedBuf`: fallible to build, fixed in length, no `Clone`, and zeroed.** The assistant's choices, 2026-10-12, queued for the engineer's review in durable-ioring's `DI-9.7`; the item is `IB-1.4` and the boundary it sits in is [IB-D-3](#ib-d-3). **`zeroed(len, align)` and `from_bytes(bytes, align)` return `Result<_, AlignedBufError>`**, where `windows-namespace-request-sys`' `AlignedBuffer` panics on a bad alignment and aborts when the allocator fails. The reason is who calls: a consumer sizing buffers from a device's reported geometry is handed the alignment by something outside the program, and a bad value is an input to refuse, not a bug to crash on; and a request too large for the machine is one a caller can recover from by asking for less. The error is non-exhaustive and has three reasons a caller reacts to differently -- `InvalidAlignment` (not a power of two, zero included), `TooLarge` (the length rounded up to the alignment does not fit an `isize`, so no allocation could be that large), and `AllocationFailed` (a valid request the allocator refused). **No `Clone`**, and `try_clone` instead: copying an I/O buffer is an allocation that can fail, and one worth seeing at the call site. **Fixed length**: there is no way to grow one. The traits' obligation is a stable address and a fixed length while an I/O layer holds the value, and a growable buffer would make that a runtime question; a caller who needs another size makes another buffer. **Zeroed or copied only**: the traits require every byte to be initialised, and a constructor that did not zero would put that on the caller. **`Deref` to `[u8]`**, so a buffer is used as a slice; `Debug` shows the length and alignment and never the contents, since an I/O buffer routinely holds someone's data; equality is by contents and alignment, not address. **A length of zero allocates nothing** and has a non-null aligned dangling address, so it is legal wherever a zero-length operation is. **Alignments** are any power of two the allocator can honour; the tests exercise every one from byte alignment to 64 KiB, and the allocator decides beyond that. **Tested for a leak** by a counting allocator the test binary installs, since a missed free is invisible to every assertion but one that counts. **Not built:** an uninitialised constructor, and a pooled or arena form; neither is excluded, and each would be a separate type if a consumer's measurements asked for it. |
