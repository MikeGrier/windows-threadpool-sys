# Design notes: win-volume-sys (Tier 1)

Current canonical decisions for this crate. See [README.md](README.md) for what it is and
[CHECKLIST.md](CHECKLIST.md) for what is planned.

Repository-level decisions this crate sits under: the `win-` prefix and what `-sys` promises, both in
the workspace [DESIGN-NOTES.md](../../DESIGN-NOTES.md#new-crates-take-the-win-prefix), and the
repository's rule to call documented APIs only, in
[copilot-instructions.md](../../.github/copilot-instructions.md). The crate was proposed on
2026-10-14 when durable-ioring's raw volume backing
([DI-10.2](../durable-ioring/CHECKLIST.md)) needed the disks a volume sits on, which only a device
control reports, and the engineer chose a new crate to hold the `unsafe` over any existing one.

## Decision index

| ID | Decision |
|---|---|
| <a id="wv-d-1"></a>WV-D-1 | **Scope widened by [WV-D-5](#wv-d-5); the rest stands.** **The crate wraps the device controls a volume answers and nothing it can already be opened for.** The engineer, 2026-10-14: "unsafe home: sounds good, do it". **Here:** `volume_disk_extents` (`IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS`), `bytes_per_sector` (`IOCTL_DISK_GET_DRIVE_GEOMETRY`), `lock_volume` and `unlock_volume` (`FSCTL_LOCK_VOLUME`, `FSCTL_UNLOCK_VOLUME`). Every one is documented, which the repository's rule requires. **Not here:** opening a volume, because `std::fs::OpenOptions` already opens `\\.\C:` and `\\?\Volume{...}` with whatever flags a caller needs, so a wrapper would add a place to be wrong and nothing else; and any statement about what a volume warrants, which is the using crate's, as the `-sys` promise requires. **Why a crate and not a place inside durable-ioring's driver:** that crate forbids `unsafe` ([DI-D-4](../durable-ioring/DESIGN-NOTES.md#di-d-4)), and the mono-repo rule is to put a call no lower crate wraps in a lower crate. |
| <a id="wv-d-2"></a>WV-D-2 | **Every control takes any handle that lends itself, needs no access for the two queries, and is the same call whether the handle was opened overlapped or not.** A handle opened with `access_mode(0)` can be asked for a volume's extents and sector size, which an account that is not an administrator can open, so the answer that decides a backing's flush domains is not gated on privilege. **The call is made with an `OVERLAPPED` and an event of its own and waited for**, because a device control on an overlapped handle with no `OVERLAPPED` is undefined, and this crate is lent handles whose open mode it cannot inspect (and may not, by the repository's rule: the call that reports it is undocumented). The wait is to completion, so the buffer and the `OVERLAPPED` are never written to after the function returns. A sabotage that drops the `OVERLAPPED` survives, declared: the volumes the tests open take it without incident, and so does `FSCTL_REQUEST_OPLOCK`, the one control that pends, which blocks inside `DeviceIoControl` and answers the same, so no test can tell the two apart. |
| <a id="wv-d-3"></a>WV-D-3 | **An answer is checked against what it says it holds, the call is never made with room for fewer than one extent, and a retry is bounded.** Reconciled on 2026-10-15 by `WV-2.2` with `D-21` of the namespace crate's [DESIGN-NOTES.md](../windows-namespace-request-sys/DESIGN-NOTES.md), which decided the same thing for its copy of this function and had two checks this one lacked; `D-21` is superseded by this row. **The reply** is a count then that many extents. `volume_disk_extents` reads the count from the header and refuses, as `InvalidData` and without reading, a count whose extents do not fit in the bytes the call said it wrote, **a call that says it wrote more than the buffer it was given** (before this, a slice that would have panicked), a negative offset or length, and an answer too short for its header; it never reads outside its buffer. **The call is never made with room for fewer than one extent**: a buffer smaller than the count plus one extent is `ERROR_INVALID_PARAMETER` on the machine measured, and not `ERROR_INSUFFICIENT_BUFFER` or `ERROR_MORE_DATA`, so the first answer has room for at least one, and **a reply that needs more room but counts none is asked again with room for one**, not for none. **A count that does not fit** is the device's `ERROR_MORE_DATA` with the count written, read through `win-error-codes`, and is asked for again at that size, up to `ATTEMPTS`, since a volume whose extents change between calls could otherwise be asked for forever; any other failure is the device's own error, ends the attempts, and is not retried. **A count whose buffer cannot be allocated** is `ERROR_NOT_ENOUGH_MEMORY` and the call is not made again, because the count is the device's and is not trusted to be allocatable. **Measured on 2026-10-15**, Windows 11, one disk, a handle opened with no access: the system volume reports one run, and every buffer size from 0 up to one byte short of the count plus one extent is `ERROR_INVALID_PARAMETER`. **Not observed:** a volume that spans or stripes disks, so the `ERROR_MORE_DATA` half, the count written with it, and the order of several runs are from the documentation and are tested against a stand-in device built to answer that way, whose one measured behaviour is the refusal above. The namespace crate's entry reported the same refusals as typed `Malformed` and `Unstable` variants; here they are `InvalidData`, as the rest of this crate reports an answer that does not hold what it says. |
| <a id="wv-d-4"></a>WV-D-4 | **A volume that answers `volume_disk_extents` is local.** A volume on a remote system, or a handle that is not a volume, does not answer the control, so success is what shows a handle names a volume on this machine's own disks. The crate says so; what to do with it is the using crate's. |
| <a id="wv-d-5"></a>WV-D-5 | **The crate's scope is physical disks, partition management, raw partition access and volume management, and those operations live here and not in the namespace crate.** The engineer, 2026-10-15: "keep it all together, physical disks, partition management, raw partition access, volume management", and "move volume-oriented operations into the volume crate". That list is wider than volumes, so the crate's name now undersells it; **renaming is not decided** (see below). **The storage-locality entries built in [windows-namespace-request-sys](../windows-namespace-request-sys/CHECKLIST.md) as `NR-2.1` to `NR-2.5` and `NR-2.7` (volume NUMA, disk extents, the storage-property queries, the virtdisk dependency query) and the overlapped-safe `DeviceIoControl` helper they share move here**, because that crate's charter is namespace operations and a volume operation does not belong in it. `NR-2.6` ("decide between the two copies") is closed by this: one helper, here, and the namespace crate's copies are deleted. This crate does **not** depend on the namespace crate. The move is [WV-M2](CHECKLIST.md#wv-m2----take-in-the-storage-locality-entries). |
| <a id="wv-d-6"></a>WV-D-6 | **A handle that must be shared is a [`SharedHandle`](../win-shared-os-owned-handle/README.md).** The engineer, 2026-10-15: "using the shared-os-owned-handle crate's type(s) is the repo's paradigm so that would seem like the right solution in general". It is an `Arc<OwnedHandle>`, so a clone is a reference-count increment and not a `DuplicateHandle`, and it makes no claim about how the handle was opened, which is what [WV-D-2](#wv-d-2) needs. It implements `AsHandle`, so the functions here keep taking `&impl AsHandle`; a consumer that needs a handle on more than one thread holds a `SharedHandle` and lends it. The namespace crate's `CapturedHandle` (a duplicate owned per request, since deleted by its [D-32](../windows-namespace-request-sys/DESIGN-NOTES.md#d-32)) and its `Request` trait are not carried over: a closure that captures a `SharedHandle` clone is how work moves to another thread. |
| <a id="wv-d-7"></a>WV-D-7 | **Every device control goes through one helper, made the same way on any handle, and a failure carries its code exactly.** From `D-20` of the namespace crate's [DESIGN-NOTES.md](../windows-namespace-request-sys/DESIGN-NOTES.md), where it was built and proven for `NR-2.1` and `NR-2.2`, and amended by [WV-D-2](#wv-d-2)'s facts about this crate. Implemented by `WV-2.1` (`src/device_control.rs`), which deletes `control()`. **The call:** every control gets its own `OVERLAPPED` and a manual-reset event and is waited for, because the crate cannot see how a handle it is lent was opened; the event is passed with its **low bit set**, which `GetQueuedCompletionStatus` documents as suppressing the completion packet, so a handle on a consumer's completion port gets none for a call the consumer never made (`control()` did not do this); a call still running is waited for with `WaitForSingleObject` and its result read with `GetOverlappedResult`, and **if that wait fails the process aborts**, because the device may still write into memory that unwinding would release. **An input buffer:** an empty one reaches the device as a null pointer and a length of zero. **A failure is an `io::Error` built from the code the call set, read in the statement after the call**, and exact for every code through `win-error-codes` ([WE-D-1](../win-error-codes/DESIGN-NOTES.md#we-d-1)), `ERROR_MORE_DATA` and `ERROR_INSUFFICIENT_BUFFER` included, which a control that reports a size first is sized by. **A buffer over 4 GiB is `InvalidInput`**, where the namespace crate's copy panicked. **The reply helpers** `u32_at`, `zeroed_output`, `invalid_data` and `is_more_data` live with it, so the functions that read a reply share one definition of each: a buffer sized from a device's own count is allocated fallibly, so the failure is `ERROR_NOT_ENOUGH_MEMORY` for the caller and not an abort. **The pending path is pinned through a seam**: the helper is `device_control`, the `DeviceIoControl` argument list, and `overlapped_call`, which owns the event, the `OVERLAPPED`, the wait and the result read and takes the call as a closure, so the tests hand it an overlapped `ReadFile` on a named pipe, which pends until the other end writes; `FSCTL_REQUEST_OPLOCK` reaches `DeviceIoControl` itself through the pending path and shows the input arriving. **Not pinned, and said so:** a control made without its `OVERLAPPED` (see [WV-D-2](#wv-d-2)), the abort when the wait fails, and the failure of `CreateEventW`, which the helper's own event cannot provoke. |
| <a id="wv-d-8"></a>WV-D-8 | **`volume_numa_node` reports the node as the device wrote it, and decides nothing about a value or a failure.** Implemented by `WV-2.3` (`src/volume_numa.rs`), from `NR-2.1` of the namespace crate, which has no decision row of its own. **What the answer is:** the node of the volume that *contains* the file or directory the handle names (or of the volume, if the handle is one); it says nothing of where a file's extents are, and a volume that spans several disks still gets one answer, so it is not evidence about each of them. **What is not decided:** the documentation does not say what a volume that advertises no proximity domain answers, so a failure is the device's own code, unaltered, and a success carries the value written, `u32::MAX` included; whether a value means "no node" is the caller's. **The reply is one `ULONG`**; a call that succeeds and says it wrote any other number of bytes is `InvalidData` and is not read, because a value taken from a buffer the device did not fill would read as a node. **The shape differs from the namespace crate's:** a `u32` and not a `VolumeNumaInfo` with a `Display` and a typed `Unexpected` error, since the function is one number and the rest of this crate returns numbers (`bytes_per_sector`) and reports a malformed answer as `InvalidData` ([WV-D-3](#wv-d-3)). **Measured on 2026-10-15**, Windows 11, one NUMA node, a Hyper-V guest: a file on the system volume answers node `0`; the `NUL` device is refused with `ERROR_INVALID_FUNCTION`; a directory and a file on the same volume answer the same; an overlapped handle answers as a plain one. **Not observed:** a volume that advertises no proximity domain, and a machine with more than one node, so whether a volume there reports the right node is not tested. **Not pinned, declared:** the control code itself, since a wrong code and a volume with no answer are both a refusal, so no test that holds on every machine tells them apart; the sabotage that changes it `survives`. What is pinned on every machine is the room the call is made with: a refusal for want of room is never the answer. |
| <a id="wv-d-9"></a>WV-D-9 | **A storage property is one call with a function per property, the reply names its own size, and the reply is reported as bytes the device gave.** Implemented by `WV-2.4` (`src/storage_property.rs`, the shared mechanics, with `src/storage_unique_id.rs`, `src/storage_numa.rs` and `src/storage_query.rs`), from `D-22` and `D-23` of the namespace crate's [DESIGN-NOTES.md](../windows-namespace-request-sys/DESIGN-NOTES.md), which are superseded by this row. **One call, a function each:** `IOCTL_STORAGE_QUERY_PROPERTY` returns a different structure per property id, so each property is its own function with its own typed reply, and what they share is private. **`query_storage_property` is the generic one**: the property and the query type are chosen by the caller, newtypes over the raw values so one cannot be passed for the other, and neither is validated, since a value the device does not know is the device's own failure; additional parameters follow the query structure's fixed fields and are passed as given; the reply is a `Vec<u8>`, empty for a query that returns no structure, where success means the property exists. The namespace crate's `StoragePropertyReply` (a wrapper with a `version` and a `size` read from the header) is not carried over, since the bytes are what the caller has. **The reply starts with its own size.** Every reply begins with a `STORAGE_DESCRIPTOR_HEADER`. The call asks once with 512 bytes (the one reply measured for the unique id was 112) and again at the size the header names, in a loop bounded at four attempts, and **never asks with room for less than the header**. A reply that is not what it says is `InvalidData` and is not read: a size below the header, a call that claims more bytes than the buffer, fewer than a header, a reply shorter than the size it names in a buffer that had room, a request for more room that names a size already given, and a size that kept changing. **The size protocol is a property's, not the call's.** Measured, and different for the two properties tried: a buffer between the header and the reply is `ERROR_MORE_DATA` with the header written for the unique id and a success with the header alone for the NUMA node, and a buffer below the header is `ERROR_BAD_LENGTH` for the first and `ERROR_INSUFFICIENT_BUFFER` for the second; the loop reads the size from whichever comes back, so it needs to know neither, and a test pins the difference so it is not forgotten. **The unique id's sections are bytes, not parsed.** The reply is a five-`u32` header (`storduid.h`, which `windows-sys` does not carry, so it is laid out here from the documentation) and up to three sections its offsets point to, each beginning with its own version and size and each checked to lie within the reply; an offset of zero means the section is absent, which is a reading of the measurement (the documentation does not say) and of zero being where the header is. What an identifier inside a descriptor is, and which of them a key for a disk is made from, is the caller's; typed accessors for the identifiers inside a descriptor are not provided (the engineer, 2026-10-15: "at this time, no. We can revisit later if necessary."). **The disk NUMA node is asked per disk**: a volume that spans disks has one answer from `volume_numa_node` and a node per disk from here, and one node for a volume whose disks sit on different nodes would be a fiction. The reply is the three `u32`s of `STORAGE_DEVICE_NUMA_PROPERTY`, returned as a struct with public fields (`version`, `size`, `node`) and the node unaltered, so no value is invented to mean "none"; the property's description names no reply structure, which is stated where it is claimed. **Measured on 2026-10-15**, Windows 11, one disk, a handle opened with no access: both properties answer on a plain and an overlapped handle alike, and an ordinary file is `ERROR_INVALID_PARAMETER` and the `NUL` device `ERROR_INVALID_FUNCTION`; the disk reports its device id descriptor and neither of the other two sections; the NUMA reply is twelve bytes and the node is zero, on a machine with one node; an exists query on a real property succeeds with nothing written whatever the output size, and an unknown property is `ERROR_INVALID_FUNCTION` for the exists and the standard question; a mask query and a query type Windows does not define were refused by both properties tried; additional parameters are ignored by the device property and read by the unique-id property, where the first byte gave the usual reply for 0, a larger one for 1 and `ERROR_INVALID_PARAMETER` for larger values, which is also how the bytes are shown to arrive, and what the byte selects is not documented. **Not observed:** a disk that reports a device descriptor or a drive layout signature, one on another bus (NVMe, USB, a virtual disk), a reply larger than the first buffer, and a machine with more than one node; those shapes are tested against constructed replies of the documented layout and a stand-in device that answers as the real one was measured to. **Documented, with a caveat:** the control code and the property ids are documented, and the documentation marks the unique-id property as intended for driver use; its reply structure is documented in the driver kit, not the Win32 SDK headers, which is the documented route to it. |
| <a id="wv-d-10"></a>WV-D-10 | **The dependency query is its own function, the version is an input, and names are copied out of the reply and never followed.** Implemented by `WV-2.5` (`src/storage_dependency.rs`), from `D-24` of the namespace crate's [DESIGN-NOTES.md](../windows-namespace-request-sys/DESIGN-NOTES.md), which is superseded by this row. **It is `GetStorageDependencyInformation`, not a `DeviceIoControl`**: a documented virtdisk call (`windows-sys` feature `Win32_Storage_Vhd`), so [WV-D-7](#wv-d-7)'s helper is not involved. It returns its status as the return value, not as `BOOL` followed by `GetLastError`, and the function reads it that way. **The code is carried exactly**: a handle that is not on a virtual disk gets `ERROR_VIRTDISK_NOT_VIRTUAL_DISK` (`0xC03A0015`) for `HOST_VOLUMES`, a named Win32 error whose value is 2^31 or more, and the `io::Error` carries it through `win-error-codes` ([WE-D-1](../win-error-codes/DESIGN-NOTES.md#we-d-1)). **The shape**: `storage_dependency_information(handle, flags, version)` and `storage_dependency_information_with_capacity`, which sets the size of the first buffer for a caller who would rather not rely on the regrow, which is unverified. The namespace crate's request type, its builder, `Request` and its typed `Malformed`/`Unstable` errors are not carried over, and the version is a parameter where the builder defaulted it to 2; a malformed reply and a size that kept changing are `InvalidData`. **The version is an input.** The call fails with `ERROR_INVALID_LEVEL` unless the buffer's version field is 1 or 2 when it is made, so the function sets it, and `StorageDependencyVersion::from_raw` carries any other value to the device to refuse. **The first buffer is never below the structure.** A buffer under `size_of::<STORAGE_DEPENDENCY_INFO>()` (72 bytes) is `ERROR_INVALID_PARAMETER` and writes nothing, not even the size, so the first size is raised to that. On `ERROR_INSUFFICIENT_BUFFER` or `ERROR_MORE_DATA` the call is asked again at the size it wrote, up to four attempts, and a size that is not larger than the one it asked with is refused. **Names are copied out and never followed.** A version 2 entry holds four `PWSTR`s. They are read as addresses, compared against the address of the reply, and used as offsets into it; a name outside the bytes the call said it used, or one with no terminator inside them, is `InvalidData` and is not read. The result holds owned `Wtf16String`s, so nothing a caller keeps points into a buffer that is gone, and a null pointer is `None`; the reply is read from an `io_buffers::AlignedBuf` because the structure holds pointers. This crate therefore depends on `wtf-string` and `io-buffers`. **Flag and type values are raw-carrying newtypes**: `StorageDependencyFlags` and `DependentDiskFlags` name the documented bits and keep the rest, and nothing is defaulted on a caller's behalf. **Not documented, and stated where it is claimed:** the documentation does not say the name strings lie inside the buffer the caller gives; a variable-length structure with a size parameter suggests it, and nothing here can show it. The function's behaviour does not depend on it being so, since a pointer outside the reply is refused and not dereferenced. **Measured on 2026-10-15**, Windows 11, a Hyper-V guest, not elevated, no virtual disk attached, handles opened with no access: a volume, a root directory and a disk handle each answer success with zero entries and the version echoed back, for both versions, in a 72-byte buffer; a version other than 1 or 2 is `ERROR_INVALID_LEVEL`; every buffer size below 72 that was tried (0, 8, 12, 16, 24, 40, 64, 65 and 71) is `ERROR_INVALID_PARAMETER`; `HOST_VOLUMES` is `0xC03A0015` on all four handles; and `DISK_HANDLE` on a volume is `ERROR_INVALID_PARAMETER`. **Not observed, and not deferred:** an entry. Attaching a virtual disk needs an elevated token, which this machine's account does not have, so no real entry's layout, no placement of its strings, no ancestor level, and no reply to a buffer too small for entries were seen. The function is tested against replies built from the structure's declared layout and a stand-in device that checks what it is asked, and [sabotage.json](sabotage.json) says the same. A run with an elevated token on a machine that can attach a VHD would turn each of these into an observation. |
| <a id="wv-d-11"></a>WV-D-11 | **`storage_device_number` reports the device type, number and partition number as the device wrote them, and success shows a handle is a volume or a disk.** Implemented by `WV-3.1` (`src/device_number.rs`). The engineer, 2026-10-18, "build both of these now", so that a caller can tell a volume or a disk from a file, which `GetFileType` does not (it reports a disk file for all three). **Sources read that day:** the control's page (`ms.date` 08/18/2022) and the structure's (03/29/2018). **The three fields are carried unaltered.** The structure's page gives `0xFFFFFFFF` for a device number on the disks that represent the physical paths of an MPIO disk and for the partition number of a device that cannot be partitioned, so neither is turned into an `Option` or read as a count, and what a value means is the caller's, as for [WV-D-8](#wv-d-8). **No access to the handle is needed**, as for the crate's other queries ([WV-D-2](#wv-d-2)). **A handle that is not a volume or a disk is the device's own error**, which is what makes success a test of kind: as [WV-D-4](#wv-d-4) says of the extents, the crate states that, and what to do with it is the using crate's. **Observed on 2026-10-18**, Windows 11 build 26300, one disk, handles opened with no access: the system volume reported the number of a disk its extents name and a partition number other than `0xFFFFFFFF`, a disk opened by number reported that number, and an ordinary file was refused. A volume on several disks, an MPIO disk and a device that cannot be partitioned were not observed, so the values the page gives for them are from the page and are tested against replies built from the structure's layout. **No work is queued behind this.** |

## Working positions

Not decisions: nothing binds to them.

- **The crate's name.** `WV-D-5` widens the scope past volumes. Whether to rename is open, and depends on whether anything has released under the current name; that has not been checked.
- **Typed `Volume` and `Disk` wrappers over a `SharedHandle`.** They would make a wrong-handle call (extents on a disk, a unique id on a volume) unrepresentable, where today it fails at run time with `ERROR_INVALID_FUNCTION`. Too early to say: the plain functions work with a `SharedHandle` already, and what a consumer composes is in `win-durable-ioring`'s volume and disk backends, which have not been read for this.
- **Errors.** The functions here return `io::Error`, and a caller who wants the code reads it with `win-error-codes`' `Win32Error::from_io`, which is exact for every code ([WE-D-1](../win-error-codes/DESIGN-NOTES.md#we-d-1)); the helper ([WV-D-7](#wv-d-7)) already works this way. A reply that does not hold what it says is `InvalidData`; the crate does not invent a Win32 code for a condition Windows did not report.
