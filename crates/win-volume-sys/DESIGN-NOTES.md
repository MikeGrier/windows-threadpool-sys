# Design notes: win-volume-sys (Tier 1)

Current canonical decisions for this crate. See [README.md](README.md) for what it is and
[CHECKLIST.md](CHECKLIST.md) for what is planned.

Repository-level decisions this crate sits under: the `win-` prefix and what `-sys` promises, both in
the workspace [DESIGN-NOTES.md](../../DESIGN-NOTES.md#new-crates-take-the-win-prefix), and the
repository's rule to call documented APIs only, in
[copilot-instructions.md](../../.github/copilot-instructions.md). The crate was proposed on
2026-10-14 when durable-ioring's raw volume backing
([DI-10.2](../durable-ioring/CHECKLIST.md)) needed the disks a volume sits on, which only a device
control reports, and the engineer chose a new crate to hold the `unsafe` over any existing one.

## Decision index

| ID | Decision |
|---|---|
| <a id="wv-d-1"></a>WV-D-1 | **Scope widened by [WV-D-5](#wv-d-5); the rest stands.** **The crate wraps the device controls a volume answers and nothing it can already be opened for.** The engineer, 2026-10-14: "unsafe home: sounds good, do it". **Here:** `volume_disk_extents` (`IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS`), `bytes_per_sector` (`IOCTL_DISK_GET_DRIVE_GEOMETRY`), `lock_volume` and `unlock_volume` (`FSCTL_LOCK_VOLUME`, `FSCTL_UNLOCK_VOLUME`). Every one is documented, which the repository's rule requires. **Not here:** opening a volume, because `std::fs::OpenOptions` already opens `\\.\C:` and `\\?\Volume{...}` with whatever flags a caller needs, so a wrapper would add a place to be wrong and nothing else; and any statement about what a volume warrants, which is the using crate's, as the `-sys` promise requires. **Why a crate and not a place inside durable-ioring's driver:** that crate forbids `unsafe` ([DI-D-4](../durable-ioring/DESIGN-NOTES.md#di-d-4)), and the mono-repo rule is to put a call no lower crate wraps in a lower crate. |
| <a id="wv-d-2"></a>WV-D-2 | **Every control takes any handle that lends itself, needs no access for the two queries, and is the same call whether the handle was opened overlapped or not.** A handle opened with `access_mode(0)` can be asked for a volume's extents and sector size, which an account that is not an administrator can open, so the answer that decides a backing's flush domains is not gated on privilege. **The call is made with an `OVERLAPPED` and an event of its own and waited for**, because a device control on an overlapped handle with no `OVERLAPPED` is undefined, and this crate is lent handles whose open mode it cannot inspect (and may not, by the repository's rule: the call that reports it is undocumented). The wait is to completion, so the buffer and the `OVERLAPPED` are never written to after the function returns. A sabotage that drops the `OVERLAPPED` survives, declared: the volumes the tests open take it without incident, so no test can tell the two apart. |
| <a id="wv-d-3"></a>WV-D-3 | **An answer is checked against what it says it holds, and a count the bytes cannot hold is refused.** `volume_disk_extents` reads its count from the header and refuses a count whose extents do not fit in the bytes the device wrote, a negative offset or length, and an answer too short for its header, as `InvalidData`; it never reads outside its buffer. A count that does not fit the first answer is the device's `ERROR_MORE_DATA`, with the count written, and is asked for again at that size, up to a small bound, since a volume whose extents change between calls could otherwise be asked for forever. The first answer has room for one extent at the least, since the device answers `ERROR_INSUFFICIENT_BUFFER`, not `ERROR_MORE_DATA`, below that. A volume with more extents than the first answer holds is a spanned or striped one, which a development machine rarely has, so the retry is tested against a stand-in device. |
| <a id="wv-d-4"></a>WV-D-4 | **A volume that answers `volume_disk_extents` is local.** A volume on a remote system, or a handle that is not a volume, does not answer the control, so success is what shows a handle names a volume on this machine's own disks. The crate says so; what to do with it is the using crate's. |
| <a id="wv-d-5"></a>WV-D-5 | **The crate's scope is the storage stack under a file system, and operations on it live here and not in the namespace crate.** The engineer, 2026-10-15: "keep it all together, physical disks, partition management, raw partition access, volume management", and "move volume-oriented operations into the volume crate". That is the volumes, the partitions on them, raw partition access and the physical disks beneath, so the crate's name now undersells it; **renaming is not decided** (see below). **The storage-locality entries built in [windows-namespace-request-sys](../windows-namespace-request-sys/CHECKLIST.md) as `NR-2.1` to `NR-2.5` and `NR-2.7` (volume NUMA, disk extents, the storage-property queries, the virtdisk dependency query) and the overlapped-safe `DeviceIoControl` helper they share move here**, because that crate's charter is namespace operations and a volume operation does not belong in it. `NR-2.6` ("decide between the two copies") is closed by this: one helper, here, and the namespace crate's copies are deleted. This crate does **not** depend on the namespace crate. The move is [WV-M2](CHECKLIST.md#wv-m2----take-in-the-storage-locality-entries). |
| <a id="wv-d-6"></a>WV-D-6 | **A handle that must be shared is a [`SharedHandle`](../win-shared-os-owned-handle/README.md).** The engineer, 2026-10-15: "using the shared-os-owned-handle crate's type(s) is the repo's paradigm so that would seem like the right solution in general". It is an `Arc<OwnedHandle>`, so a clone is a reference-count increment and not a `DuplicateHandle`, and it makes no claim about how the handle was opened, which is what [WV-D-2](#wv-d-2) needs. It implements `AsHandle`, so the functions here keep taking `&impl AsHandle`; a consumer that needs a handle on more than one thread holds a `SharedHandle` and lends it. The namespace crate's `CapturedHandle` (a duplicate owned per request) and its `Request` trait are not carried over: a closure that captures a `SharedHandle` clone is how work moves to another thread. |

## Working positions

Not decisions: nothing binds to them.

- **The crate's name.** `WV-D-5` widens the scope past volumes. Whether to rename is open, and depends on whether anything has released under the current name; that has not been checked.
- **Typed `Volume` and `Disk` wrappers over a `SharedHandle`.** They would make a wrong-handle call (extents on a disk, a unique id on a volume) unrepresentable, where today it fails at run time with `ERROR_INVALID_FUNCTION`. Too early to say: the plain functions work with a `SharedHandle` already, and what a consumer composes is in `win-durable-ioring`'s volume and disk backends, which have not been read for this.
- **Errors.** The functions here return `io::Error`, and a caller who wants the code reads it with `win-error-codes`' `Win32Error::from_io`, which is exact for every code ([WE-D-1](../win-error-codes/DESIGN-NOTES.md#we-d-1)). A reply that does not hold what it says is `InvalidData`; the crate does not invent a Win32 code for a condition Windows did not report.
