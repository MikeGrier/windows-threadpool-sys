# Design notes: fixed-hash-table (Tier 1)

Current decisions for this component. What it is: [README.md](README.md). The work: [CHECKLIST.md](CHECKLIST.md). The crate
was decided in durable-ioring's [DI-D-106](../durable-ioring/DESIGN-NOTES.md#di-d-106), which holds the engineer's rulings;
the conversation is the Tier 3 record,
[DESIGN-SESSION-2026-10-22-durable-ioring-no-std-and-preallocation.md](../../design-sessions/DESIGN-SESSION-2026-10-22-durable-ioring-no-std-and-preallocation.md#capacity-and-the-tables-continued-2026-10-23).
This component keeps Tier 1 only, with the rationale folded into each decision. Decisions FHT-D-3 to FHT-D-8 are the
assistant's, made when the crate was created, and confirmed by the engineer, 2026-10-23, each with "yes".

## Decision index

| ID | Decision |
|---|---|
| <a id="fht-d-1"></a>FHT-D-1 | **Hash tables whose capacity is fixed when made, which refuse an insert when full.** Made for durable-ioring's tables ([DI-D-106](../durable-ioring/DESIGN-NOTES.md#di-d-106)), so that nothing allocates after construction and being full is an answer, not a growth. **Named by the engineer:** "build, put it in a separate crate, call it fixed-hash-table". **Scope**, the engineer: "it should support as much of the usual collection affordances as possible, trimmed towards no-std, no-alloc, with generics to allow for clients who do want std and alloc." A map and a set. Sequence-keyed tables, which may want a slab or a ring, are durable-ioring's DI-23.10 and not decided here. |
| <a id="fht-d-2"></a>FHT-D-2 | **`no_std` and allocation-free by default; `alloc` and `std` are additive features.** Without them a table's storage is inline. `alloc` adds storage allocated once, fallibly, when the table is made; `std` adds what needs it, such as conversions for `std`'s hasher. CI's `portable` job builds, tests and lints the crate on Linux and macOS. |
| <a id="fht-d-3"></a>FHT-D-3 | **Storage is a type parameter**: inline, as a const-generic array of slots, or (under `alloc`) a boxed slice allocated when the table is made and never again. The table's operations are written once over a slice of slots, so the two differ only in where the slice lives. The alternative, a separate table type for each storage, was rejected: it would restate every operation. |
| <a id="fht-d-4"></a>FHT-D-4 | **Open addressing with linear probing, and backward-shift deletion**, so a removal leaves no tombstone and a table that churns does not degrade. **Capacity and slots are distinct**: a table holds at most its declared capacity and refuses past it, while its slot count is larger, so a probe always finds an empty slot and probe lengths stay short. The slot count is a power of two at most seven-eighths full; for inline storage the slot count is the const parameter and the capacity is derived from it. |
| <a id="fht-d-5"></a>FHT-D-5 | **The hasher is a `core::hash::BuildHasher` type parameter**, held by value, as the engineer asked: "a generic T which can provide a functor that does not vary by instance and saves storage as well as allow for an instance which permits per collection functors". A zero-sized `BuildHasher` is the per-type functor and costs no storage; one with state is per table. **The default is a zero-sized, seedless hasher of the crate's own**, since `no_std` has no seed to draw on; a client whose keys an adversary chooses supplies a keyed one, `std`'s `RandomState` among them. |
| <a id="fht-d-6"></a>FHT-D-6 | **No `unsafe`, enforced by `#![forbid(unsafe_code)]`.** A slot is an `Option` of the entry, which costs a discriminant per slot where `MaybeUninit` would not; the safety of a hand-managed slot array is not worth that saving here. |
| <a id="fht-d-7"></a>FHT-D-7 | **A full table refuses by handing back what it was given**: `insert` returns the key and value in its error, so nothing is dropped and a caller can act on it. An insert that replaces an existing key's value never needs room and is never refused. |
| <a id="fht-d-8"></a>FHT-D-8 | **The affordances `std`'s `HashMap` and `HashSet` offer, where they make sense without growth**: lookup, mutable lookup, removal, `contains`, an entry API whose vacant insert is fallible, iteration (shared, mutable, consuming, keys, values), `retain`, `drain`, `clear`, `len`, `capacity`, `Debug`, `Clone`, `PartialEq`, `Eq`, `Extend` as a fallible `try_extend`, and `Index`. **Left out:** what only growth gives -- `reserve`, `shrink_to_fit`, an infallible `insert` -- and `FromIterator`, which would have to choose a capacity or panic. |
